# Harness Engineering

<p class="ailab-title-subtitle">- 네 기둥을 하나의 장치로 설계하기</p>

앞 절에서 하네스를 이루는 4가지 기둥

- Context
- 권한/실행
- 멀티에이전트
- 외부연결

들을 익혔습니다.

이 문서는 위 4가지 요소를 **하나의 조작 장치로 설계하는 관점**을 다룹니다.

하네스가 무엇인지의 정의는 [Harness란 무엇인가](what-is-harness.md)에서 이미 봤으니, 여기서는 **무엇을 어떻게 조율할 것인가**에 집중합니다.

## 네 기둥은 서로 다른 질문에 답한다

하네스를 설계한다는 것은 네 기둥에 각각 다른 질문을 던지고 답을 채우는 일입니다.

기둥마다 답하는 질문이 다르므로, 설계자가 부품을 고를 때 **이건 어느 기둥의 문제인가**를 먼저 정의해야 합니다.

| 기둥 | 답하는 질문 | 부품 | 설계 깊이 |
|---|---|---|---|
| Context | 무엇을 넣을 것인가 | CLAUDE.md · MEMORY.md · Skill | [Context Engineering](context-engineering.md) |
| 권한/실행 | 무엇을 허용하고 무엇을 강제할 것인가 | Rule · Hook | [권한 모드와 슬래시 명령](../claude-code/permissions-and-commands.md) · [Loop Engineering](loop-engineering.md) |
| 멀티에이전트 | 일을 어떻게 나누고 격리할 것인가 | Subagent | [Subagent 개념](what-is-subagent.md) |
| 외부연결 | 무엇에 연결할 것인가 | MCP | [MCP 로 외부 데이터 연결](../mcp/what-is-mcp.md) |

## 하네스는 신입사원에게 일을 맡기는 것이다

하네스를 설계할 때 조정할 수 있는 각 설정값을, 이 절에서는 신입사원에게 업무를 맡기는 정도에 비유합니다.

그중 첫 번째는 **에이전트에게 무엇까지 맡길 것인가**를 정하는 조작입니다.

신입사원에게 처음에는 사소한 일까지 하나하나 확인시키다가, 믿음이 쌓이면 점점 더 큰 일을 통째로 맡기는 것과 같습니다.

가장 먼저 맡기는 일은 **권한 모드**입니다.

`default`·`acceptEdits`·`plan` 을 상황에 맞게 바꾸는 것만으로도, 같은 요청이 "매번 확인받는 일"이 되기도 하고 "알아서 처리하는 일"이 되기도 합니다.

쉽게 말하면

- `default` 는 "중요한 일은 매번 물어봐",

- `acceptEdits` 는 "파일 편집은 알아서 해",

-  `plan` 은 "먼저 계획만 세우고 실행은 멈춰"

처럼 위임 범위를 정하는 지시입니다.

모델 선택·토큰 예산·작업 폴더 경계·샌드박스도 같은 성격의 위임 범위 조정입니다

자세한 조작은 [권한 모드와 슬래시 명령](../claude-code/permissions-and-commands.md)에서 다룹니다.

설계의 요령은 **한 번에 다 맡기지 않는 것**입니다.

처음엔 설계자가 작은 범위의 일을 맡기고, 반복되는 작업에서만 위임 범위를 넓힙니다.

## 하네스는 낡고, 자산은 남는다

하네스를 구축한다는 것은 **"현존하는 모델이 못 하는 것을 하네스로 해결하자"는 가정**을 담습니다.

그래서 모델이 좋아지면 그 가정이 낡습니다.

Haiku 로 못 하던 작업을, 더 똑똑한 모델인 Opus 나 Fable 로 바꾸면 하네스 없이 풀리기도 합니다.

이 사실이 설계 방향을 정합니다. **갈아끼우는 부품(하네스 조작)이 아니라, 사용자는 남는 자산(context · loop)에 투자해야 합니다.**

- 판정 기준·업무 규칙·워크플로는 사용자가 파일(Context)로 남깁니다 → 모델이 바뀌어도 그대로 씁니다.
- 스스로 검증하고 고치는 절차는 사용자가 루프(Loop)로 남깁니다 → [Loop Engineering](loop-engineering.md)에서 네 부품으로 분해합니다.

하네스 조작법은 버전이 오르면 바뀌지만, 잘 정의한 기준과 루프는 다음 모델에서도 자산으로 이어집니다.

## (심화) 네 기둥을 한 번에 포장·전파하기 - Plugin

!!! note "지금은 건너뛰어도 됩니다"
    이 절은 직접 만든 부품을 팀에 나눠 주거나 남에게 배포할 때 필요합니다 - 혼자 쓰는 단계라면 넘어가도 됩니다.

네 기둥에 걸쳐 만든 부품(skill · agent · hook · MCP)은 흩어진 채로 두면 나 혼자만 씁니다.

이것들을 하나로 묶어 남에게 건네는 배포 단위가 **Plugin** 이고, 그 플러그인을 나누는 장터가 **Marketplace** 입니다.

비유하자면 여러 도구를 상자 하나에 담아 건네는 것이 Plugin 이고, 그 상자들을 올려 두고 서로 가져가는 앱 장터가 Marketplace 입니다.

- 묶고 배포하는 절차 → [Plugin 만들고 배포하기](plugin-creation.md)
- 배포처를 여럿에게 여는 방법 → [Marketplace 개념](marketplace.md)

즉 하네스 설계는 "네 기둥을 채우기 → 위임 범위로 조율하기 → 자산으로 남기기 → 플러그인으로 전파하기"의 순서로 완성됩니다.
